PROJECT POSITIONING · 项目定位

它解决校医室的什么问题？

校园医务室人流集中、问题琐碎：症状评估、预约排班、常见病咨询、复诊提醒……全压在前台，而这份工作应当先由智能体完成 80%，医生只处理真正需要面诊的部分。

AN INTELLIGENT FRONT-DESK THAT HANDLES TRIAGE, BOOKING & Q&A

系统承担的前台工作链路

  • 登录与会话隔离 —— 手机验证码登录，UUID Token 鉴权，多用户并行互不干扰
  • 症状收集与追问 —— 结构化采集症状细节，像医生一样追问
  • 初步风险识别 —— 红旗症状实时拦截，优先升级处理
  • 预约与排班匹配 —— 专科匹配、可用时段分配、改约 / 取消
  • 健康知识检索问答 —— 基于 100 万医学问答向量的 RAG 答疑
  • 健康追踪与复诊建议 —— 问诊记录沉淀，驱动后续复诊提醒
边界 · 系统刻意「不做」什么
不替代医生诊断输出默认保守，只做辅助建议与初步评估
不输出「无需预约」等绝对否定性医疗结论医学安全约束贯穿系统提示与返回层
高风险症状立即转急救胸痛、呼吸困难、昏迷等 7 大类红旗症状，优先提示 120 / 急诊

FROM A SYMPTOM SENTENCE TO AN EVIDENCE-BASED APPOINTMENT

医学任务自动分类

TASK CLASSIFICATION

将用户输入实时识别为 doctor / appointment / faq / emergency / chat 五类意图，决定交给哪个 Agent 处理。

多 Agent 分工协作

MULTI-AGENT ORCHESTRATION

中心分类 Agent 统筹调度，问诊、预约、问答各由专注的专家 Agent 独立完成，单一职责、上下文隔离。

流式可解释输出

STREAMING & EXPLAINABLE

流式返回结构化 Token（思考过程 / 最终回复 / 快捷按钮），用户的每一步推理都透明可见、可打断。

RAG 医学问答

RETRIEVAL-AUGMENTED Q&A

先检索 100 万医学问答向量再做生成，回答有证据支撑；检索不到就坦诚求助医生，绝不编造。

症状追问式诊断

SYMPTOM-BASED CONSULTATION

腹痛、头痛等复杂症状启动结构化追问（最多 3 轮），基于已收集信息给出诊断可能性，再给建议；简单症状直接给建议。

按症状推荐科室

SYMPTOM → DEPARTMENT MATCH

症状确认后按症状智能推荐科室（肚子疼→内科、牙疼→口腔科），推荐结果跨请求保留，流转顺畅。

红旗症状风险升级

RED-FLAG ESCALATION

胸痛、呼吸困难、昏迷等危急词被实时捕获，弹窗不可一键关闭，须确认「拨打 120 / 立即就医」后强制进入紧急引导模式。

医生排班与预约

SCHEDULE & BOOKING

医生可用性查询、时段智能分配、冲突检测与改约 / 取消；时间缺失时拒绝臆造、强制询问补齐。

GLM JSON Mode 预约解析

STRUCTURED LLM OUTPUT

预约信息解析接入 GLM JSON Mode 结构化输出，字段结构稳定、杜绝臆造科室 / 时间（实测臆造率 0%）。

无状态 Agent · 会话隔离

STATELESS AGENT + SESSION

Agent 无状态，会话与插槽全部外置 Redis；Token 多用户并发，进程崩溃也不丢失对话进度。

健康追踪与复诊建议

HEALTH FOLLOW-UP

沉淀每次问诊记录，从历史中学习偏好，给出复诊 / 随访 / 紧急就医等分级推荐。

医生数据档案

DOCTOR PROFILE

16 位校园专科医生的学科、职称、学历、执业年限、评分结构化入库，支持值班与排班管理。

ENGINEERING HIGHLIGHTS · 工程亮点

几个「硬核」设计决策

每一处取舍，都让系统更稳、更可扩展、更适合校园场景落地。

DESIGN DECISIONS THAT SCALE

无状态 Agent 设计

STATELESS AGENTS · STATE IN REDIS

Agent 进程本身不存任何状态，对话进度、插槽、摘要全部外置，换来优雅的水平扩展。

# 状态全部落在 Redis，TTL 自动过期
state:{"user_id"}:{"conversation_id"} → appointment
auth:token:{token} → user_id / conversation_id
  • 同一会话串行执行，跨会话并行不互扰
  • 进程崩溃重启，对话进度不丢失
  • 多实例水平扩展，天然支撑多用户并发

Zilliz Cloud 向量检索 + RRF

MILVUS MANAGED · HYBRID SEARCH

生产走 Zilliz Cloud（Milvus 云托管），100 万条 768 维向量免自建；检索用 Milvus 内置 INVERTED 全文检索 + 向量召回 + RRF 融合。

VECTOR_DB_TYPE = milvus   # Zilliz Cloud Public Endpoint
向量召回 ∪ 全文召回 → RRF 融合排序
Milvus INVERTED + TEXT_MATCH 中文关键词
  • 100 万医学问答向量，768 维（PCA 降维）
  • 本地 / 云端向量库只改一个配置
  • 混合检索弥补纯向量 / 纯关键词的盲区

本地离线 Embedding + PCA

BGE-M3 · 1024 → 768-DIM

FlagEmbedding 引入 BGE-M3（1024 维）离线生成向量，再经 PCA 降维至 768 维存储，大幅降低检索开销。

FlagEmbedding → BGE-M3 1024维
PCA 降维 → 768维（解释方差 0.9968）→ 向量库
查询同链路降维，保证召回一致
  • 校园 / 隔离内网也能离线完成 embedding
  • 维度减 25%，云向量库存储成本更低
  • 查询端加载同一 PCA 模型，结果不失配

医学安全约束层

MEDICAL SAFETY ENGINEERING

红旗症状 7 大类别，客户端 + 服务端双重检测；风险事件双持久化并强制进入紧急引导，直到用户确认已就医。

risk_events 表写入 + Redis 标记（双持久化）
弹窗不可一键关闭 → 强制紧急模式 → 急救引导
  • 只做辅助建议，不做最终诊断
  • 不输出「无需预约」等绝对排除性结论
  • 风险事件留存，可审计、可追踪

跨厂商 LLM Provider 工厂

MULTI-LLM PROVIDER FACTORY

一个工厂方法统一装配各家对话与 Embedding 模型，切换厂商不动业务代码。

providers = qwen · deepseek · zhipu · openai
             · openai-compatible · azure · volcengine
默认 openai-compatible，chat / embedding 分别配置
  • 国内模型可直连，网络环境更友好
  • 适配 DeepSeek 思考模式（该模式自动关闭 JSON Mode）
  • 模型替换仅一处配置，利于成本与质量调优

流式输出 · 低首字延迟

ASYNC STREAMING CHAT

FastAPI 异步生成器把回复分片流式推给前端，思考过程逐步可见、可打断。

AsyncGenerator → token 流
[THOUGHT]… [REPLY]… [BUTTONS]…
  • 首个字符即返回，等待感大幅下降
  • Agent 思考链透明，用户建立信任

Langfuse 全链路可观测性

LLM OBSERVABILITY

所有 LLM 调用（分类 / 预约解析 / 问诊建议 / 追问分析）自动接入 Langfuse 云托管，记录完整 trace。

model_provider.py 统一挂载 CallbackHandler
trace = prompt + 输出 + token + 耗时
未配置 key → 优雅降级，不影响运行
  • 每个回答可回溯到输入与模型调用链
  • token 与耗时可视化，便于成本监控
  • 一键开关，无需改动业务代码
